# Contributing

`ovos-test-harness` proves that a combination of cross-repo branches conforms
to the [`OpenVoiceOS/architecture`](https://github.com/OpenVoiceOS/architecture)
specs. Start at [docs/testing-combos.md](docs/testing-combos.md) — it is the
entry path for the workflow this repo exists to support: picking a branch
combination, editing `requirements.txt`, and reading the conformance verdict
from a PR.

Before writing a new test, read
[docs/writing-conformance-tests.md](docs/writing-conformance-tests.md).

## Setup

```bash
sudo apt-get install -y swig libfann-dev   # padatious needs these to build
pip install -r requirements.txt
pytest test/ -v --tb=short
```

## The "always glob, never name" rule

CI must always discover test files by glob (`pytest test/`,
`test/backcompat/**`, `test_*_conformance.py`, and so on), never by naming an
individual file. A hardcoded filename in a workflow silently stops running
the moment that file is renamed or split, and the suite reports green while
covering less than it did before. If you add a new conformance module, a new
backcompat cell, or a new channel-gaps case, it must be picked up by the
existing globs with no workflow edit required. If it isn't, fix the glob —
do not add the filename.

## Back-compat matrix xfail discipline

`test/backcompat/` (the mixed-version matrix workflow — see
[docs/ci.md](docs/ci.md)) certifies real cross-version compatibility, and its
`xfail` markers ARE the sprint backlog for closing compat gaps
(`FINDINGS/SPRINT.md`, generated by the workflow's `summarize` job, reads
every xfail/xpass in the suite). That only works if every marker in the file
follows the same rules:

1. **Every expected failure is `xfail(strict=True)`.** No bare `xfail`, and
   no `skip` used as a stand-in for xfail. Strictness is what turns "the fix
   shipped" into a loud red (an XPASS) instead of a silent, easy-to-miss
   green.
2. **Every xfail reason should follow the `boundary_xfail(...)` convention**
   — `boundary=`, `axes=`, `blocked_on=`, `owner=`, `note=` — once that
   helper exists. As of this writing it is not yet defined in `driver.py`
   (owned by an in-flight branch); until it lands, write the reason as
   prose that still names the boundary, the blocked-on issue (if any), and
   what an XPASS means, the way `test_mixed_version_matrix.py`'s existing
   reasons already do. `test/backcompat/findings.py`, which feeds
   `FINDINGS/SPRINT.md`, parses either form — the structured call form when
   present, a best-effort heuristic (an `owner#issue` token) otherwise — so
   older prose reasons keep showing up in the sprint feed even before every
   marker is migrated. Do not add or invent `boundary_xfail` yourself in
   `driver.py` as part of an unrelated change; that helper's shape belongs
   to whichever PR actually introduces it.
3. **A red cell is never deleted, renamed away, or silenced to make a PR
   green.** Dropping backwards compatibility for a boundary is a real,
   deliberate decision — it means flipping the `xfail` marker (or removing
   it) *in the same commit* that drops the compat guarantee, naming the
   boundary being dropped in the commit message. A red cell disappearing
   without that is a regression in the harness, not a fix.
4. **Every xfail's boundary must be a real one.** It should name (or link)
   an entry in the back-compat design doc's boundary-archaeology table (the
   verified list of "last pre-spec" / "first post-spec" releases per
   component). An xfail whose boundary isn't traceable to a real,
   verified crossing is measuring an accident of the test fixture, not a
   real compat gap — treat that as a bug in the test, not a finding.
5. **XPASS means the fix shipped, not "investigate a flake."** A `strict`
   xfail turning green is executable proof the boundary closed. The
   response is to drop the marker (and, if the boundary was the whole
   reason a cell existed, consider whether the cell now belongs in the
   passing-controls set), not to treat it as noise to silence.

## Branches

- `dev` — active development, open PRs here.
- Feature branches merge into `dev` as draft PRs; a maintainer reviews and
  merges.

## Commit style

This project uses [Conventional Commits](https://www.conventionalcommits.org/):

- `feat:` new functionality
- `fix:` bug fixes
- `chore:` maintenance (deps, CI, packaging)
- `docs:` documentation only

## Pull requests

- Target the `dev` branch.
- Keep `requirements.txt` diffs reviewable: one ref change per line, with a
  comment explaining why (see [docs/how-it-works.md](docs/how-it-works.md)).
- Do not edit `docs/coverage.md` or `docs/known-gaps.md` by hand outside a
  conformance-suite change — they track what the test suite actually proves.
- Validate any workflow YAML you touch:
  `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/<file>.yml'))"`.
